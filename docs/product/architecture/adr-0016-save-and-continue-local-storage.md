# ADR-0016: Save and continue in browser localStorage (S-010)

- Status: Accepted (peer review: cycle 1 conditionally approved, cycle 2 conditionally approved; all findings folded in, max 2 cycles)
- Date: 2026-10-26
- Deciders: nWave solution-architect (S-010 DESIGN, `interaction_mode=propose`)
- Related: ADR-0003 (functional core, imperative shell; its "Future persistence" note is taken here), ADR-0005 (squads derived on demand, frozen order), ADR-0006 (frozen attribute tables), ADR-0008 (focus plan), ADR-0009 (optional state fields), ADR-0010 (schedule), ADR-0011 (match model, streams, goldens), ADR-0012 (the results log; "persistence ... validates shape, a separate story with its own probe"), ADR-0014 (derived `nextMatchday`; "a future persistence story must validate shape, order and contiguity of a loaded log, with its own `probe()`"), ADR-0015 (`NewGame` from `seasonEnd`).
- **Amends** (status-line notes only): ADR-0003, ADR-0005, ADR-0006, ADR-0011 (their frozen data is now save-relevant), ADR-0012 (D9 "no persistence yet"; Earned Trust 3 "Future persistence"), ADR-0014 (Earned Trust 4), ADR-0015 (its "no storage" statement). Everything else in them stands.

## Context
S-010 (DISCUSS D1-D10, US-1, US-2) makes a season span visits. Binding rules:
- **D1**: after a club is picked, the game is saved automatically after each saving tap (club picked, formation chosen, Starting XI player picked, Play match). Saved: seed, club, formation, XI (with picks), results. Not saved: the screen.
- **D2/D3**: the title shows "Continue" (44px or taller) above "New game" only with a saved game; "Continue" lands on the club home of the saved club, heading focused, everything as before the reload; the continued season equals the uninterrupted one.
- **D4**: "New game" starts fresh from the address's seed; the save is replaced only once a club is picked in the new game.
- **D5**: one slot; "Continue" ignores the address's `?seed=`; "Play again" after "Continue" keeps the saved league.
- **D6**: an unreadable save gives no "Continue". Storage blocked or full **when the game loads** (a *degraded* store) gives no "Continue" (a readable older save is then not offered), the game plays without saving, and it makes a best-effort, silent removal of the stored save at load and on each saving tap, so a later visit never finds an older save (residual: when access is blocked entirely nothing can be removed, so a save that existed before is offered again once access returns). A save that fails **during play** removes the stored save (best effort, silently), so "Continue" never offers a state older than the last one played (exceptions: the removal also fails, access is blocked entirely, several tabs open); later saving taps try again. A failed save never interrupts play and logs no console error.
- **Guardrail**: a full saved season stays under 64 KB (about 1% of a 5 MB quota).

Facts checked in the code:
- `GameState` is exactly `{ league, screen, formation, xi?, results? }`; `tests/acceptance/S-009/existing-navigation-unchanged.test.ts` asserts no other key, and tests may never be weakened. The managed club exists only as the screen's `clubId`, so a save is a projection of the state while the screen carries a club.
- `results` is `PlayedMatch[]`, 4 entries per matchday in fixture order, each `{ matchday, fixtureIndex, home, away, result: { homeGoals, awayGoals, goals: { minute, side, playerIndex }[] } }`: plain JSON-able data (ADR-0012 tests the JSON round trip). `matchday`, `fixtureIndex`, `home`, `away` are determined by the entry's position and the frozen schedule (ADR-0010); the two scores equal the goal counts by side.
- `topScorer` throws `RangeError` for a goal naming a player outside the squad, `main.ts` `scorerName` throws for an unknown player, and `render` throws for an unknown club. A loaded log must therefore be validated before it reaches the state (S-009 Open question).
- `update` is at 13 cases (complexity 14 of 15); `main.ts` `render` is at 15 of 15 (S-009 Open question 1). `.oxlintrc.json` forbids `localStorage` in `src/domain/` only. There is no storage code anywhere in `src/`.
- The match model, squads, attributes and the AI-side policy are frozen by ADRs 0005, 0006, 0010, 0011 and 0012, and **guarded in CI by existing goldens** (ADR-0011 seed-31 and seed-20260 matches, the S-007 table, the S-008 reference season, the S-009 summaries): a change to any of them turns CI red and needs an ADR.
- GitHub Pages serves every project of a user from one origin (`<user>.github.io`), and `localStorage` is per origin, so the key must be namespaced.
- `stryker.config.mjs` and `playwright.config.ts` are not in the locked list of CLAUDE.md (only `.github/`, `factory/`, `docs/product/brief.md`, `docs/product/scope.md`, `scripts/`, `.nwave/`, `CLAUDE.md`, `tests/protected/`); only `scripts/factory/protected.playwright.config.ts` is locked.
- Browser behaviour relied on (MDN, Web Storage API; from the architect's knowledge, **not looked up in this unattended run, which had no browsing tool**): reading the `localStorage` property can throw `SecurityError` when storage is blocked; `getItem` returns `null` for an absent key; `setItem` can throw `QuotaExceededError` when storage is full or disabled; `removeItem` normally still works when storage is full; values are strings.

## Options

### 1. What is stored
| Option | Pros | Cons |
|---|---|---|
| **A. The recorded results as they are: a plain versioned envelope `{ v, seed, clubId, formation, xi?, results? }` with `results` the `PlayedMatch[]` log unchanged (chosen)** | One representation of a result everywhere (state, save, tests): no second schema to keep in step, no compress/expand transform, the ADR-0012 JSON round trip is already tested, a stored file is readable by a human. About 230 bytes per match: about 13 KB for an average season (2.73 goals per match, 45 bytes per goal) and about 51 KB if every chance scored in every match, under the 64 KB guardrail | Five fields per entry repeat what position and counts already say; each must be cross-checked on decode (cheap: equality with `fixturesOf` and the goal counts) |
| B. Irredundant: only the per-match goal lists as `[minute, side 0/1, playerIndex]` triples in schedule order | About 32 bytes per match (about 1.9 KB average, 10.5 KB worst case); redundant fields cannot disagree | A second schema and a transform in each direction that must track `PlayedMatch`; harder to read and to debug; solves a size problem the relaxed 64 KB guardrail no longer has. Rejected on the reviewer's finding: complexity for no required benefit |
| C. Per-matchday choices (formation, XI) and replay the whole season | Smallest | The history of past XIs is not in `GameState` (adding it breaks the five-key test) and is not recoverable; couples every save to the current model |
| D. A full `GameState` snapshot including `league` and `screen` | No projection logic | Stores derivable data (league, names); stores the screen (D1 says no); hides name-pool changes behind stored names |

Envelope: one object, `v` the integer format version (`SAVE_VERSION` = 1). `xi` is present only when the player changed the XI (absent means "follows the formation", ADR-0009). `results` is present only when at least one matchday is recorded. Key order is fixed by the encoder and entries are rebuilt in canonical key order on decode, so equal states encode to equal text. One `localStorage` key: **`gaffer.save`** (namespaced; the origin is shared with other projects of the same user).

### 2. How strictly a stored save is validated
| Option | Pros | Cons |
|---|---|---|
| A. Shape and ranges only | Smallest | Accepts a log whose fixtures are not the schedule, whose scores disagree with its goals, or that skips a matchday; `nextMatchday`, the table and `topScorer` would then lie or throw |
| **B. Structural truth (chosen)** | Covers corruption, truncation, hand editing, version skew, with no dependency on the match model: every rule is a fact the format itself states (see Decision) | Cannot tell that a well-formed log was produced by an older match model |
| C. B plus replay-verify: re-play every recorded matchday and compare the three fixtures that do not involve the managed club | Would turn unannounced model drift into "unreadable save" | Rejected on the reviewer's finding (H-1, M-5): it couples decode to the current model and to the AI-side XI policy, so an intentional change that does not invalidate saved facts (ADR-0012: "what is played stays played") would silently delete players' seasons; the managed fixture cannot be replayed (past XIs unknown), so it is only a partial check; it pulls `save.ts` into `state.ts`, `match.ts` and every squad generator for a risk CI already guards (see Context). Not needed |
| D. Full replay | Strongest | Impossible: the managed club's XI per matchday is not recorded |

Model drift is handled by process, not by the decoder: any ADR that intentionally changes squads, streams, the match model or the AI-side policy in a way that makes saved results wrong must bump `SAVE_VERSION` (old saves then read as "no saved game", no migration); an unannounced change turns an existing golden red in CI. The residual risk (a model change that is not caught by any golden and not bumped) is accepted: a save would continue with its old recorded results and the new model for the rest of the season.

### 4. How "Continue" enters the state machine
| Option | Pros | Cons |
|---|---|---|
| **A. A `Continue` action carrying the already-validated restored `GameState` (what `decodeSave` returned at boot): valid only from `title` (then the state becomes the payload), else a `toBe` no-op; together with turning `update`'s switch into a handler table so `update` has headroom (chosen)** | Every transition, including this one, runs through `update`, so `focusPlan` (title to club home is a screen change, so the club home `<h1>` is focused, ADR-0008) and the loop are unchanged; the title renderer just dispatches; the no-op and swap are unit-testable; the five-key test is untouched (no new state key); `update` complexity drops from 14 to 1 | A "rehydrate"-style action carries a whole state (guarded to the title screen; only `decodeSave` constructs it; a grep test pins the one dispatch site) |
| B. The shell swaps `state` outside `update`; the title renderer takes an `onContinue` callback | `update` untouched | A transition outside the pure core, a second path to repeat `focusPlan`, a renderer that takes a bare callback instead of `dispatch` (breaks the `render<Screen>(root, props, dispatch)` convention); e2e-only |
| C. `Continue` action *without* the lookups refactor | Smallest diff | `update` lands at exactly 15 of 15 with zero headroom; S-009 Open question 1 ("the next action must first move `update` ... to lookups") is ignored and the debt compounds |
| D. `Continue` carries the raw `SaveData` and `update` calls `fromSave` | One validation path | The state machine re-validates and regenerates on every call; `update` would depend on `save.ts` (and `save.ts` on `state.ts`): an import cycle |

**Decision on S-009 Open question 1 (recorded here): it is closed for `update` only.** `update` moves to a handler table now (this story adds its action). `render` stays a switch at 15 of 15: no screen is added, and the title case only gains a prop (no branch). Converting `render` to a lookup is deferred to the next story that adds a *screen*, which must do it first. `ci:lint` is the gate for both counts.

### 5. What triggers a write, and what a failed write does
| Option | Pros | Cons |
|---|---|---|
| **A. A pure `saveTextFor(lastText, state)` in `save.ts` returns the text to write, or `undefined` (screen without a known club, or text equal to the last read or written); the adapter's `autosave` performs the effect inside one silent try, remembers the new text on success and **`undefined` on failure** (so the next dispatch re-attempts), and a failed write removes the stored save, best effort (chosen)** | D1's triggers and D4's timing fall out of the data (a no-op pick or the same formation changes nothing; `NewGame` and "Play again" reach `pickClub`, which has no club; "Continue" writes nothing); the decision is a pure function tested in Node; no list of action names; D6's "never offer an older state" holds as best effort; a later tap retries and, because the failure forgot the text, also retries an earlier text (T1 saved, T2 fails, back to T1 writes T1); the removal also frees space | One `JSON.stringify` of at most about 51 KB per tap (microseconds); a failing store is retried on every following dispatch (a swallowed no-op) |
| B. A whitelist of action types | Cheap | Writes on no-ops, couples the shell to action names, misses any future saving action |
| C. Write on every dispatch | Simplest | Needless churn on a phone |
| D. Write on `visibilitychange` / `pagehide` only | Few writes | Unreliable on mobile (tab discarded without events): the failure S-010 exists to remove |
| E. Leave the old save in place on a failed write | Simplest adapter | Violates D6: "Continue" would offer a state older than the last one played |

### 6. The storage technology
`localStorage` (scope.md IN). Rejected: IndexedDB (asynchronous, heavy, nothing to index for about 13 KB), cookies (4 KB cap, sent with requests, no server needs them).

## Decision
**1A, 2B, 3A, 4A, 5A, 6 localStorage.** No new dependency; browser API only.

### App, pure: `src/app/save.ts` (CREATE NEW)
- `SAVE_VERSION = 1`. `SaveData = { v, seed, clubId, formation, xi?, results? }` (plain JSON data; `results` is `readonly PlayedMatch[]`).
- `toSave(state: GameState): SaveData | undefined`: `undefined` unless the screen carries a `clubId` that is in the league. Otherwise projects seed, club, formation, XI (only if stored) and the log (only if non-empty), in fixed key order.
- `fromSave(raw: unknown): GameState | undefined`: designed to be total (never throws). In order: envelope shape (object, `v === SAVE_VERSION`, `seed` an int32 integer, `clubId` a string, `formation` a known id); regenerate the league from the seed (`generateLeague`) and require the club in it; `xi`, when present, an array that is legal for the club's squad and formation (`isLegalXI`, EXTEND `selection.ts`); `results`, when present, a non-empty array whose length is a multiple of 4 and at most 56 (14 matchdays), where **entry `i` must have `matchday` = `i / 4` + 1 (integer division), `fixtureIndex` = `i % 4`, `home` and `away` equal to `fixturesOf(matchday)[fixtureIndex]`** (so the log is contiguous 1..N with exactly 4 per matchday, in fixture order, the fixtures being the schedule's), `homeGoals` and `awayGoals` integers 0..9 **equal to the goal counts by side**, and every goal `{ minute: integer 1..90, side: "home" | "away", playerIndex: integer 0..17 }` with minutes non-decreasing. A valid squad index is the only player check (no position rule; cheap and enough to keep `topScorer` and `scorerName` from throwing). Unknown extra keys are ignored; entries are rebuilt in canonical key order. Any failure returns `undefined`; no partial restore. The restored state is `{ league, screen: { kind: "clubHome", clubId }, formation, xi?, results? }` with the optional keys present only when stored, so it holds no key beyond the existing five.
- `encodeSave(state): string | undefined` (`toSave` then `JSON.stringify`). `decodeSave(text: string | null | undefined): GameState | undefined`: **one try/catch around both `JSON.parse` and `fromSave`**, returning `undefined` on any throw (defence in depth: `fromSave` is designed total, the catch makes the guarantee unconditional for the boot path, and `main.ts` calls only `decodeSave`).
- `saveTextFor(lastText: string | undefined, state: GameState): string | undefined`: the pure write decision: `encodeSave(state)` when it is defined and differs from `lastText`, else `undefined`.
- The law: for every reachable state `s` on a screen with a known club, `fromSave(JSON.parse(encodeSave(s)))` `toEqual`s `s` with `screen` set to the club home; `update` is a pure function of state and action, so a continued season equals the uninterrupted one by construction (K2).

### App: `src/app/state.ts` (EXTEND)
- `Action` adds `{ type: "Continue"; game: GameState }`. Handler: from `title`, return `action.game`; from any other screen, the same state (`toBe`). `focusPlan` is untouched.
- `update` becomes a handler table keyed by `Action["type"]` and typed so a missing key is a compile error. Behaviour-preserving: every existing handler function is unchanged, and the S-001..S-009 `update` suites pass unedited. One documented cast at the lookup (TypeScript cannot correlate the union).
- `GameState` is unchanged. (No `sidesFor` split: replay-verify was dropped.)

### Domain, pure: `src/domain/selection.ts` (EXTEND)
- `isLegalXI(squad, formation, xi): boolean`: 11 distinct integers 0..17 with `squad[xi[i]].position === lineUp(formation)[i]`. A rule about selections, so it sits with `pickForSlot` and under Stryker's domain glob. `src/app/seed.ts` exports its existing `isInt32`.

### Adapter, effectful: `src/adapters/save-store.ts` (CREATE NEW, the first driven adapter)
- `createSaveStore(getStorage: () => SaveStorage, key = "gaffer.save"): SaveStore`, with `SaveStorage = Pick<Storage, "getItem" | "setItem" | "removeItem">` (capability injection: never `window`). The factory is the only constructor and **probes during construction** (wire, probe, then use). `SaveStore = { health: "ok" | "degraded"; read(): string | undefined; write(text: string): boolean }`.
- `probe` (inside the factory): obtain the storage through the getter, write a sentinel to a second key (`gaffer.probe`), read it back and require equality, remove it. Any throw (getter, `setItem`, `getItem`, `removeItem`) or a mismatch makes the store `degraded`: `read()` always returns `undefined` and `write()` returns `false`. This is D6's "blocked or full when the game loads: no Continue, a readable older save is not offered, play without saving". **A degraded store still cleans up after itself**: if the storage getter itself worked (the probe failed on `setItem`, `getItem` or a mismatch, e.g. a full store), the factory makes one best-effort, silent `removeItem("gaffer.save")` at construction, and a degraded store's `write()` makes the same silent removal on each saving tap before returning `false`, so a later visit never finds an older save. Residual (stated, accepted): when the getter itself throws (access blocked entirely) nothing can be removed, so a save that existed before is offered again once access returns.
- When `ok`: `read()` returns the stored string, or `undefined` (absent, not a string, or a throw). `write(text)` stores the text and returns `true`; on any throw it **removes the stored save (`removeItem`, itself try/caught), and returns `false`**, silently. Nothing is ever logged (D6, `no-console`).
- Deliberate deviation from the generic "refuse to start" rule (Earned Trust, `health.startup.refused`): saving is optional; D6 requires the game to play as before, so a failed probe degrades silently instead of refusing.
- `createAutosave(store, lastText): (state: GameState) => void`: the whole step (`saveTextFor`, the encode inside it, and `store.write`) runs inside **one silent try**, so nothing can reach `dispatch`. On success the remembered `last` becomes the written text; **on a failed write (or a throw) it becomes `undefined`**, so the next dispatch re-attempts, including an earlier text: with T1 saved, T2 failing, and the state back at T1, T1 is written again (`last` = T1 would have wrongly skipped it). The removal in `write` also frees space. The stored game is therefore the last played state or absent, as best effort: if the removal also fails (or access is blocked entirely) the previous save remains, a stated residual.
- Boot, in `main.ts` (composition root): `store = createSaveStore(() => localStorage)`; `stored = store.read()`; `offer = decodeSave(stored)`; `autosave = createAutosave(store, stored)`; after each `dispatch`, `autosave(state)`. These are the only storage reads and writes of the page (one read, one probe round trip, then writes of `gaffer.save`).

### UI: `src/ui/screens/title.ts` (EXTEND), `src/ui/styles.css`, `src/main.ts`
- `renderTitle(root, { offer }, dispatch)` with `dispatch` narrowed at compile time to `NewGame` and `Continue`. With an offer: `section.title-screen` = h1 "Gaffer" (still focused on load), tagline, `button.primary` "Continue" (dispatches `{ type: "Continue", game: offer }`), `button.secondary` "New game". Without an offer the markup is exactly today's (`button.primary` "New game" only), so every protected scenario that starts in a fresh context sees an unchanged title. `.secondary` is the outlined gold button of `.back-button` with the title's `min-width: 200px`.
- `main.ts`: the `title` case passes `{ offer }` (a module constant read at boot; the title is never shown again after a page load, because no action returns to it). `render` gains no branch.
- After "Continue" the loop focuses the club home `<h1>` (the club's name) through `focusPlan`; renderers still never move focus.

### Determinism
No new stream, draw, clock or randomness. The league is regenerated from the saved seed, so "Play again" after "Continue" (`NewGame` keeps `league`) keeps the saved seed (D5). `nextMatchday` is derived from the restored log. The format carries no timestamp and no id.

## Consequences

### Positive
- A season spans visits; the save is the state's own data (about 13 KB average, about 51 KB worst case), with no new `GameState` key and no second schema.
- Corruption, truncation, old versions and hand edits land on one outcome: "no saved game". A failed write removes the stored save, best effort, so "Continue" does not normally offer an older state; if the removal also fails the previous save remains (stated residual).
- The adapter is the only file naming a storage API, with an injectable getter; every lie below has a fault-injection test; the write decision is pure.
- `update` goes from complexity 14 to 1, clearing the S-009 debt for actions.

### Negative
- A rehydrate-style `Continue` action carries a whole state (guarded to the title, one dispatch site).
- The decoder does not know the match model: a model change that is neither caught by an existing golden nor accompanied by a `SAVE_VERSION` bump lets an old save continue with its old results (accepted; the process rule and CI goldens are the guard). There is no migration (OUT).
- A `degraded` store also hides a readable old save (literal D6) and, when the getter works, silently removes it; when access is blocked entirely nothing can be removed and the old save is offered again once access returns (stated residual). The player is not told that saving failed (OUT).
- A failing write is retried on every following dispatch (a cheap swallowed no-op).
- **Several tabs (OUT, not tested): last write wins, and the offer is read once at boot, so a tab that still shows the title can offer a stale game after another tab played on; its "Continue" restores that older state and its next saving tap overwrites the newer save.** The shared origin means the namespaced key is a convention, not isolation.
