# ADR-0008: Focus on a same-screen update (S-004)

- Status: Accepted
- Date: 2026-10-17
- Deciders: nWave solution-architect (S-004 DESIGN, `interaction_mode=propose`)
- Refines ADR-0003 "Bootstrap" ("after each navigation, the shell moves focus to the new screen's `<h1>`"), ADR-0003's component contract for `render<Screen>` (`dispatch` gains an optional second argument) and the brief's "renderers do not move focus" contract. ADR-0003 is not superseded; the focus rule narrows from "after every render" to "after a render that changed the screen", and `dispatch` becomes `(action, focusId?) => void`.

## Context
Today `main.ts` runs `dispatch` then `update` then `render` and ends every render with `root.querySelector("h1")?.focus()`; each renderer replaces all of root's children. That is right for navigation (S-001..S-003 protected tests assert focus on the new `<h1>` after each tap). S-004 adds the first same-screen update: tapping or arrow-keying a formation radio changes state while the screen stays "Tactics". The outcome requires the heading to stay "Tactics" and focus to be on the tapped formation's radio button, also for arrow keys; a full re-render replaces the focused radio with a new node, and the unconditional `<h1>` focus would throw a keyboard or screen-reader user back to the top of the screen.

A first draft relied on reading `document.activeElement` before the render. That fails where the platform does not focus a radio on tap (Safari/iOS touch), which would have needed an "accepted limitation". The review showed it is unnecessary: the `change` listener knows exactly which input fired, so it can name the element to refocus, and programmatic `focus()` works on every browser, including iOS Safari.

## Options
| Option | Pros | Cons |
|---|---|---|
| **A. Shell rule expressed as a pure plan: heading focus only when the `Screen` changed; otherwise focus the element whose `id` the dispatching renderer named (chosen)** | Smallest change (one pure function in `state.ts`, an optional dispatch argument and a few lines in `main.ts`); renderers still never move focus (brief contract kept); works for every future same-screen widget that gives its controls stable ids; plan is unit-testable in Node; S-001..S-003 behaviour is identical (every navigation changes the screen); focus lands on the tapped radio in every browser | Controls on same-screen-updating screens must carry stable ids; the dispatch contract gains an optional argument |
| B. The tactics renderer patches the line-up and radios in place and `main` skips the re-render | The focused node is never replaced | Splits "render replaces root's children" (ADR-0002) into a second path for one screen; `main` needs a per-screen "skip render" rule; native radio state can drift from `GameState`; every later same-screen screen repeats the special case |
| C. Keyed DOM diff in the shell (or a tiny vdom) | General; preserves focus and scroll | A reactive layer for one screen; contradicts ADR-0002's "no reactivity" and its revisit trigger (the match feed, not a radio group); more code than the feature |
| D. Renderers take a "focus this id" hint and move focus themselves | Local | Breaks "renderers never move focus"; focus rules scatter across screens |
| E. Read `document.activeElement` only (the first draft of A) | No dispatch change | Nothing is focused on a tap in Safari/iOS, so focus falls back to the heading there; rejected for the extra platform-dependent branch |

## Decision
**Option A.**
- Dispatch contract: `dispatch(action, focusId?: string)`. The second argument is optional, so every existing renderer (title, pick-club, club-home, squad, player) is unchanged. `renderTactics`'s `change` listener calls `dispatch({ type: "ChooseFormation", formation }, "formation-<id>")` with the id of its own input. Renderers pass an id only; they never call `.focus()`.
- Pure `focusPlan(previous: Screen | undefined, next: Screen, focusId: string | undefined) => FocusPlan` lives in `src/app/state.ts` (next to `Screen`, no new module), with `FocusPlan` = `{ kind: "heading" } | { kind: "element"; id: string }`. Plan-value pattern: the function only returns data; `main.ts` is the only code that touches focus.
  - `previous` undefined (first render) or a different screen (compared by kind and every field, `clubId` and `playerIndex` included): `heading`.
  - Same screen and `focusId` a non-empty string: `element` with that id.
  - Same screen and no `focusId`: `heading`, so focus is never left on `<body>` (ADR-0003's original intent).
- `main.ts` keeps the previously rendered `Screen`. In its `dispatch(action, focusId?)` it takes `focusId` from its optional second argument only (no `document.activeElement` read: every same-screen dispatch in S-004 names its id, so a fallback would be unreachable). After `update` and render it calls `focusPlan(previous, next, focusId)` and executes the plan: `heading` focuses `root.querySelector("h1")`; `element` focuses the element with that id inside `root` (found after the render, so it is the new node), falling back to the `<h1>` if no such element exists. The focus happens in the same task as the render, so focus is never observably lost. Renderers keep the contract `(root, props, dispatch)` and write only root's children.
- Contract on renderers: any control that must keep focus across a same-screen re-render carries a stable, unique `id` derived from data, never from position or a counter (radios: `formation-4-4-2`, `formation-4-3-3`, `formation-4-2-3-1`), and its listener passes that id as `focusId`.
- The tactics radios dispatch from the native `change` event (not `click`), so the already-checked formation dispatches nothing (and keeps its native focus), and the arrow-key path works: the browser moves focus to the next radio and checks it before `change` fires, and the listener names that same input's id, which is restored after the re-render.
- No platform limitation is accepted in the design: the id comes from the listener, not from the platform focusing a radio on tap. Focus is on the tapped radio in Chromium (probed by e2e and the protected scenarios); iOS Safari is expected to behave the same, because programmatic focus on a native radio works there, but it is not probed in CI (an unprobed assumption). A future same-screen control that must keep focus passes its own id the same way.

## Consequences
- Positive: the S-001..S-003 focus tests hold unchanged (a navigation always changes the screen); same-screen updates keep focus on the interacted control on every browser; the rule lives in one tested pure function, not in each screen; Stryker already covers `state.ts`, so `focusPlan` is in the nightly mutation score with no owner action.
- Negative: the id convention and the optional second argument must be remembered by future screens; `state.ts` grows by one small function.
- Contract shapes: `focusPlan` pure return-only (unit tests: first render, each navigation incl. same club different screen and different player index, same-screen with id, same-screen without id; inputs not mutated). `main.ts` stays the unbounded shell; its universe is now: reads `location.search` once; writes root's children (via render) and focus (the `<h1>`, or the element with the resolved id); no other globals.
- Earned Trust (environment lies about focus): the assumption is "a re-rendered node with the same id can be focused programmatically in the same task, and a native radio group keeps exactly one checked radio". It is probed by the phone-viewport e2e, which asserts after tapping "4-3-3" that the radio named "4-3-3" is the focused element and its group still has exactly one checked radio; the arrow-key e2e (focus a radio, press `ArrowRight`, assert the next radio is checked and focused, the heading is still "Tactics"); and the focus-on-arrival checks for S-001..S-003 plus "Tactics" and "Back". Fault injected: the re-render replaces the focused node (the very thing the plan must survive). The fallback to the heading covers a missing id. iOS Safari is not a tested target, but nothing in the design depends on touch focus.
- Enforcement: oxlint boundaries (app may not import ui; `state.ts` imports no DOM); the rule "renderers never call `focus()`" is a code-review check, plus a committed unit test (DISTILL, `tests/unit/`) over `src/ui/` that fails if `.focus(` appears (cheap structural check; the e2e is the behavioural layer).
- No external integrations, no contract tests, no new dependency.
