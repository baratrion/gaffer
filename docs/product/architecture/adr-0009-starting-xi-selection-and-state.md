# ADR-0009: Starting XI selection rules and state (S-005)

- Status: Accepted (note, ADR-0016 Enforcement, S-010: the "owner-locked" description of `stryker.config.mjs` below is superseded; the file is not on CLAUDE.md's lock list, and S-010 widens its `mutate`)
- Date: 2026-10-18
- Deciders: nWave solution-architect (S-005 DESIGN, `interaction_mode=propose`)
- Related: ADR-0003 (functional core, imperative shell), ADR-0005 (d) (squad derived on render), ADR-0006 (derived overall, index-based player screen), ADR-0007 (slot = index in `lineUp`; "S-005 stores slot index to player index in state"), ADR-0008 (focus on the `<h1>` after a screen change). Amends the S-005 storage note of ADR-0007 (which now points here): the slot-to-player map is stored only once the player has changed the XI. Supersedes nothing else.

## Context
S-005 fills the 11 slots of the chosen formation with squad players. The XI starts automatic (per position, highest overall first, ties in squad order), Sam can replace or swap players within a position (tap a slot, tap a player), the XI is kept for the session, a formation change re-picks the automatic XI (DISCUSS D10, this story only), and "New game" starts from the automatic XI. Constraints:
- The squad is derived on render and never stored (ADR-0005 (d)); the rules must be pure and seed-free beyond the generated squad (no RNG, no `Date`).
- Binding DoD: no assertion in `tests/acceptance/S-004/` is edited, and choosing a formation with an XI never changed still returns `{ ...state, formation }` only. `tests/acceptance/S-004/tactics-navigation.test.ts` asserts `initialState(league)` `toEqual` `{ league, screen: { kind: "title" }, formation: "4-4-2" }`, and `tests/acceptance/S-003/player-navigation.test.ts` asserts literal whole states `{ league, screen, formation }`. Vitest `toEqual` ignores keys whose value is `undefined` but not keys holding `null`.
- `tsconfig.json` has `exactOptionalPropertyTypes`; oxlint caps `max-params` at 3 and `complexity` at 15; Stryker mutates `src/domain/**` and `src/app/state.ts` only (owner-locked config).
- Protected scenarios find buttons by role and accessible name. Playwright's default name match is a case-insensitive substring match.

## Options

### 1. The XI in `GameState`
| Option | Pros | Cons |
|---|---|---|
| **A. Optional `xi?: StartingXI \| undefined`: absent (or `undefined`) means "never changed" and the effective XI is derived on demand as `automaticXI(squad, formation)`; stored on the first real pick; dropped by a formation change and by `NewGame` (chosen)** | Follows ADR-0005 (d) (derived data not stored); an XI never changed follows the formation by construction; every existing S-001..S-004 assertion and fixture stays unedited (`toEqual` ignores an absent or `undefined` key); `ChooseFormation` on a never-changed XI is still exactly `{ ...state, formation }` | Two cases for readers (absent, stored), behind one selector; an optional field is a weaker type fact than a required one |
| B. Required `xi: StartingXI \| null`, `null` until the first pick | Explicit "never changed" marker in the type | `initialState` gains `xi: null`, so S-004's `initialState` `toEqual` and S-003's literal whole-state assertions fail: forbidden by the DoD (assertions would need editing) |
| B2. Required key `xi: StartingXI \| undefined`, `undefined` until the first pick | The key is always present; `toEqual` ignores `undefined`, so the existing assertions still pass | Every `GameState` literal in the existing acceptance tests (S-001, S-002 and S-003 fixtures and the S-003 expected states, which are typed `GameState`) must add `xi: undefined` to typecheck. The DoD allows that (fixtures may gain a field), but it is churn for no behaviour. `ChooseFormation` would return a state whose key set differs from S-004's expectation only by an `undefined`. It gives the same "never changed" semantics as A with more edits |
| C. Eager XI always stored, computed on `ChooseClub` and recomputed on `ChooseFormation` | One case for readers | Stores derivable data (against ADR-0005 (d)); `ChooseFormation` then changes `xi` too, breaking S-004's "only `formation` changes" assertions; the title and pick-club screens have no club, so the field is meaningless there |
| D. Store a sparse override map (slot to player) on top of the automatic XI | Small state | A swap must rewrite two overrides that can contradict the derived base; two sources of truth for one XI; harder property tests |

### 2. Shape of an XI
| Option | Pros | Cons |
|---|---|---|
| **A. `StartingXI = readonly number[]`: 11 squad indices in slot order, slot `i` = index `i` of `lineUp(formation)` (chosen)** | Matches ADR-0007's slot index and ADR-0006's index-based player screen (the squad order is frozen); swap is two index writes; deep-equal and JSON-comparable | The meaning depends on the frozen squad order (already frozen by ADR-0005/0006) |
| B. Map of slot to player name | Survives a squad reorder | Names are not designed as keys (ADR-0006 3B); lookup on every render; YAGNI until transfers |
| C. Store `Player` objects | No lookup | Duplicates generated data (ADR-0005 (d)); invites drift |

### 3. Where the rules live
| Option | Pros | Cons |
|---|---|---|
| **A. New pure `src/domain/selection.ts` owning D5, D6 and D8: `automaticXI`, `pickForSlot` (validates slot, index and position, then replaces or swaps), `playersForPosition`, `isSlotIndex`; `update` only routes (chosen)** | Rules in the core (ADR-0003), property-testable in Node, inside Stryker's domain glob; `update` stays one helper per action | A context object is needed to keep `pickForSlot` within 3 parameters |
| B. Rules inline in `update` (`src/app/state.ts`) | One file | Game rules in the shell state; `update` grows past one-helper-per-action; mixes routing and rules |
| C. Index-only swap in domain, eligibility (position, ranges) in `update` | Smallest domain function | Splits one rule (D5 + D8) across two layers; the "slot holds only its position" property is not a domain property |

### 4. Screens and layout
| Option | Pros | Cons |
|---|---|---|
| **A. Two new `Screen` variants, `startingXI{clubId}` and `choosePlayer{clubId, slot}`; the XI as one flat stacked list of 11 full-width buttons (chosen)** | Every tap is a screen change, so focus goes to the new `<h1>` (ADR-0008) with no focus ids; one button per line fits 390px with long names wrapping; the list count is exactly 11 | No pitch picture of the XI (the Tactics screen already shows the shape) |
| B. Expand the players inline under the tapped slot (same-screen update) | One screen | Needs focus ids for 11 slots and up to 6 players (ADR-0008 path), more state in the screen, and DISCUSS D7 asks for its own heading "Choose MF" |
| C. Pitch rows like the S-004 line-up, with names in the chips | Looks like a team sheet | 4 chips per row at 358px leave about 80px per name ("Finlay Fitch-Moreton" wraps to 3 lines); a 44px tap target per chip is hard to keep; nested rows would tempt nested lists |

## Decision
**1A, 2A, 3A, 4A.**

### Domain: `src/domain/selection.ts` (pure, no RNG, no seed of its own)
- `StartingXI = readonly number[]` (11 squad indices, slot order). `isSlotIndex(value: number): boolean`: an integer 0..10.
- `automaticXI(squad: readonly Player[], formation: FormationId): StartingXI`. For each position P, rank the squad indices of P by overall descending, ties by squad index ascending; walk `lineUp(formation)` and give each slot of code P the next ranked index of P. Positions are contiguous in `lineUp` (GK, DF, MF, FW), so within a position the slots read highest first (4-2-3-1's two MF lines are slots 5..9). The quota 2/6/6/4 covers every formation, so no slot is empty.
- `playersForPosition(squad, position): readonly number[]`: the squad indices of that position, in squad order (the choose screen's list and its order).
- `pickForSlot(selection: { squad, formation, xi }, slot: number, playerIndex: number): StartingXI | undefined` (3 parameters):
  - `undefined` (invalid pick) when `slot` is not a slot index, `playerIndex` is not an integer 0..17, or the player's position differs from `lineUp(formation)[slot]`;
  - the same `xi` object when the player already holds `slot`;
  - else a new array: if the player holds another slot `j`, the two swap (slot gets the player, `j` gets the slot's previous player); otherwise the player replaces the slot's player.
  The input is never mutated. Same position on both sides of a swap, so D5 holds by construction.
- Imports: types from `squad.ts`, `lineUp` and `FormationId` from `formation.ts`. No app or ui import (oxlint).

### App: `src/app/state.ts`
- `GameState` gains `readonly xi?: StartingXI | undefined`. `initialState` is unchanged (no `xi` key).
- `currentXI(state: GameState, squad: readonly Player[]): StartingXI` = the stored `xi`, else `automaticXI(squad, state.formation)`. It is the one place that derives the effective XI. `main.ts` (both new render cases) and `update` (`PickPlayer`) call it, so the derivation is never duplicated, and it is inside Stryker's `state.ts` glob.
- A private `withoutPicks(state)` returns `state` itself when no `xi` is stored, else `{ ...state, xi: undefined }`. `ChooseFormation` (after its unchanged guards) returns `{ ...withoutPicks(state), formation }`: with an XI never changed that is exactly `{ ...state, formation }`. `NewGame` keeps its title-only guard (from any other screen it is a no-op, as the S-004 suite asserts) and from the title returns `{ ...withoutPicks(toScreen(state, pickClub)), formation: DEFAULT_FORMATION }`. Neither adds an `xi` key when there is none.
- One club per session: `xi` is never stale across clubs because `pickClub` is reachable only through `NewGame`, which drops `xi`, and `ChooseClub` runs only on `pickClub`. Unit tests pin both halves: `ChooseClub` is a no-op on every screen but `pickClub`, and `NewGame` from a title holding a stored `xi` gives a state with no `xi`. A later "back to clubs" story must reset or key `xi` (DISCUSS D9).
- Squad lookup: `state.ts` exports `squadOf(league, clubId): readonly Player[] | undefined` (club index = position in `league.clubs`; `undefined` for an unknown club). It is the one lookup used by `PickPlayer` and by `main.ts`'s two new render cases, so the two cannot drift. `findClub` stays for the existing cases.
- `Screen` gains `{ kind: "startingXI"; clubId }` and `{ kind: "choosePlayer"; clubId; slot }`. `Action` gains `{ type: "ViewStartingXI" }`, `{ type: "ChooseSlot"; slot: number }` and `{ type: "PickPlayer"; playerIndex: number }`.
  - `ViewStartingXI`: only from `clubHome` of a known club, to `startingXI` (same club).
  - `ChooseSlot`: only on `startingXI` of a known club with `isSlotIndex(slot)`, to `choosePlayer{clubId, slot}`.
  - `PickPlayer`: only on `choosePlayer` of a known club with a valid slot. The squad is `squadOf(league, clubId)`. With `base = currentXI(state, squad)` and `next = pickForSlot({ squad, formation, xi: base }, slot, playerIndex)`: `undefined` gives the same state (no-op, stays on the choose screen; the renderers never dispatch such a pick, and if one arrived without a `focusId` the plan is `heading`, the ADR-0008 default); `next === base` (own player) gives `toScreen(state, startingXI)` with `xi` untouched (a never-changed XI stays never changed); otherwise `{ ...toScreen(state, startingXI), xi: next }`.
  - `Back`: `choosePlayer` (known club, valid slot) to `startingXI`; `startingXI` (known club) to `clubHome`; unknown club or invalid slot is a no-op, as for the player screen.
  - Every other new or old action on the new screens is a no-op. One helper per action keeps `update` under the complexity cap; `back` may be split into per-screen helpers if it nears 15.
- `focusPlan`'s `sameScreen` gains `startingXI` (compare `clubId`) and `choosePlayer` (compare `clubId` and `slot`). The switch stays exhaustive (TypeScript rejects a missing case because the function returns `boolean`). Every new navigation is a screen change, so focus goes to the new `<h1>`; no focus ids are added.

### UI (ADR-0002: `el()`, `textContent` only; renderers never move focus)
- Club home: a third `button.primary` "Starting XI" after "Tactics" in `div.club-actions`, dispatching `ViewStartingXI`.
- `ui/screens/starting-xi.ts`, `renderStartingXI(root, { slots }, dispatch)`, where `main.ts` passes `slots = lineUp(formation).map((position, slot) => ({ position, player: squad[xi[slot]] }))`: one `<h1 id="starting-xi-title" tabindex="-1">Starting XI</h1>`; `<ul role="list" aria-labelledby="starting-xi-title">` (so the list name is the heading text, from one source); 11 `<li>`, each with one `<button type="button" class="xi-slot">` dispatching `ChooseSlot{slot}`; a `.back-button` "Back".
- `ui/screens/choose-player.ts`, `renderChoosePlayer(root, { position, players }, dispatch)`, where `main.ts` passes `players = playersForPosition(squad, position).map((playerIndex) => ({ playerIndex, name, overall, starting: xi.includes(playerIndex) }))`: one `<h1 tabindex="-1">` "Choose " plus the code; `<ul role="list" aria-label="Players">` with one `<li>` and one `<button type="button" class="xi-choice">` per player, dispatching `PickPlayer{playerIndex}`; a `.back-button` "Back".
- Button text (both screens): inline spans separated by literal single-space text nodes. Starting XI: code span, `" "`, name span, `" "`, overall span. Choose: name span, `" "`, overall span, and for starters `" "` plus a "Starting" span. So `textContent` and the accessible name read exactly "MF Ivo Elderkin 18" and "Ivo Elderkin 18 Starting" (no leading or trailing space). The buttons and their spans stay in inline flow: no flex, grid or float on the button, and every span inside it keeps `display: inline` (no `inline-block` or block accents; a CSS review check). Mechanism: flex and grid items and floats are blockified, whitespace-only text nodes between flex or grid items are not rendered, and `innerText` inserts a line break around block-level boxes, so `innerText` would read "MF\nIvo Elderkin\n18". This is the same inline-flow rule the brief set for the S-003 player lines; squad rows still use a grid, so their markup is not reused. The button is `display: block`, `width: 100%`, `min-height: 48px`, `text-align: left`, `overflow-wrap: anywhere`, so long names wrap and nothing scrolls sideways at 390px.
- Accessible names: "Starting XI" contains none of "Squad", "Tactics", "Back", "Line-up", "Formation", "Clubs" or "Choose". Slot and player buttons are built from names that the DISCUSS D12 unit check keeps free of its nine words: "Back", "Squad", "Tactics", "Starting", "Players", "Formation", "Line-up", "Clubs" and "Choose", case-insensitive substrings over every string array in `names.ts`.

### Shell: `src/main.ts`
Two render cases: `startingXI` (`squadOf`, `currentXI`, `lineUp`) and `choosePlayer` (the same, plus `lineUp(formation)[slot]` and `playersForPosition`). An unknown club (`squadOf` returns `undefined`) throws "Unknown club in game state", as `findClub` does; an index that has no player, or a slot that has no code, throws, like the existing "Unknown player in game state". The state guards make all three unreachable. `render`'s switch gets a `never`-typed exhaustiveness guard (its return type is `void`, so today a missing case would compile and leave root empty). Focus handling is unchanged.

## Consequences
- Positive: no existing test assertion or fixture changes (the DISCUSS budget's 40 fixture lines are not needed); an XI never changed follows the formation by construction (D10's permanent rule); rules are pure domain functions under Stryker; every navigation is a screen change, so ADR-0008's heading rule covers focus with no new ids; no new dependency, adapter or C4 container.
- Negative: `xi` has two states (absent, stored) and readers must go through `currentXI`. The enforcers are code review, the `update` unit tests (inside `state.ts`) and the e2e for `main.ts`: a direct `state.xi[slot]` read throws on a never-changed XI, so the first Starting XI e2e fails; `update` derives the squad for `PickPlayer` (one `generateSquad` call per pick, microseconds); a later "back to clubs" story must reset or key `xi` by club (DISCUSS D9), and the D15 keep-picks story replaces `withoutPicks` in `ChooseFormation` with a re-fit rule.
- Contract shapes: `automaticXI`, `pickForSlot`, `playersForPosition`, `isSlotIndex`, `currentXI`, `squadOf`, `update`, `focusPlan` are pure return-only (deep-equal on repeat, inputs never mutated, `pickForSlot` returns the same reference for the own player). `renderStartingXI` and `renderChoosePlayer` are bounded-change (root's children only). Read-only driving ports expose no write methods.
- Properties to test (fast-check, `FC_SEED`; many seeds, all 8 clubs, all 3 formations): `automaticXI` has 11 distinct indices 0..17; `squad[xi[i]].position === lineUp(f)[i]`; within a position, overall non-increasing and ties in ascending index; no non-starter of P has a higher overall than a starter of P (and a non-starter tied with the lowest starter has a later index); goldens (checked against the generator on 2026-10-18): seed 31, club 0, 4-4-2 gives `[0, 7, 3, 6, 2, 9, 12, 8, 10, 17, 14]`; seed 31, club 0, 4-3-3 gives `[0, 7, 3, 6, 2, 9, 12, 8, 17, 14, 16]`; seed 20260 (`?seed=abc`), club 7, 4-2-3-1 gives `[1, 5, 2, 6, 7, 12, 9, 10, 8, 11, 17]`. Readers test `state.xi === undefined`, never `"xi" in state` or `Object.hasOwn` (a never-changed XI adds no key, but a dropped XI, after a pick and then a formation change or `NewGame`, is an own `xi: undefined` key). `pickForSlot`: result is 11 distinct indices, positions still match; the picked player is in the slot; a replace changes one slot and a swap changes exactly two; picking the displaced player back into the slot restores the input (involution); own player returns the same object; wrong position, index -1, 18, 1.5, NaN and slot -1, 11, 1.5 give `undefined`. `update`: the no-ops of DISCUSS D11; `ChooseFormation` with a stored XI drops it and with none adds no key; `NewGame` drops it; `PickPlayer` own player returns to `startingXI` with no `xi` key added; the S-004 suite unchanged and green.
- Earned Trust: no new adapter (no storage, clock or network), so there is no adapter probe. The one environment assumption (the browser's layout and accessibility tree) is named and probed:
  - Assumption: inline spans with single-space text nodes give an accessible name, `textContent` and `innerText` with single spaces on one line, and long names wrap within 390px.
  - Probe: the phone-viewport e2e uses exact-name queries (`exact: true`), checks each slot button's `textContent` and `innerText` equal its expected string, and checks scroll width. It uses an apostrophe name and a hyphenated name (`?seed=abc`, 8th club: "DF Ulric O'Garrity 8"; `?seed=31`: "FW Finlay Fitch-Moreton 5" in 4-3-3).
  - Faults injected in DISTILL's reference: spans without the space nodes must turn the exact-name and `textContent` checks red. `display: grid` (or flex) on the button must turn the `innerText` check red, by the blockification mechanism above; the accessible name alone is not relied on to catch it.
- Closed world for the renderers: `root.replaceChildren` is the only write (as for every renderer), and no new renderer touches `document`, `window` or focus. The `.focus(` grep and code review cover it; no DOM-diff harness is added (the e2e reads the whole screen).
- Enforcement: oxlint boundaries unchanged (selection.ts imports only domain modules; state.ts imports no ui); `max-params` 3 holds (`pickForSlot` takes a context object); the PR guard keeps `Math.random` and `Date` out of `src/domain/`; Stryker covers `selection.ts` (domain glob) and `currentXI`, `withoutPicks` and the new `update` cases (`state.ts`), with no config change; the `.focus(` grep unit test (ADR-0008) covers the two new renderers.
- No external integrations, no contract tests.
