# Gaffer: architecture brief

SSOT for architecture. Decisions live in `adr-0001..0016`; this file shows how they fit together. Extend it per story.

## Application Architecture

### Drivers and constraints
Quality attributes, in order: determinism and replayability, phone usability and accessibility, testability, small bundle, simplicity. Bundle budget: no runtime dependencies; JS under 50 kB gzip (not yet enforced by CI; deferred).
Constraints: static site under `/gaffer/`, no backend, one solo team (no Conway conflict), OSS only (TypeScript, Vite, Vitest, fast-check, Playwright, oxlint, Stryker: all MIT or Apache-2.0).

### Style (ADR-0003)
Modular monolith, run as a functional core and imperative shell. This is the functional paradigm, and it is recorded here and in ADR-0003, not in CLAUDE.md.
Ports and adapters, in function-signature form:
- `src/domain/` is the pure core. Readonly data, no DOM, clock, storage, `Math.random` or `Date`. Randomness comes only from `rng.ts`.
- `src/app/` is the pure shell state: `GameState`, `Screen`, `Action`, `update`, `initialState`, `parseSeed`, `focusPlan` (S-004, in `state.ts`), `currentXI` (S-005, in `state.ts`), and from S-007 the recorded results plus `playOpeningMatchday`, `matchFor` and `standingsOf` (in `state.ts`); from S-008 `nextMatchday` (derived from the results log, ADR-0014), and `PlayMatch` appends the next matchday; from S-009 the `seasonEnd` screen, `ViewSeasonEnd`, a `NewGame` that is also valid from that screen, and `seasonSummaryOf` (ADR-0015); from S-010 `update` is a handler table keyed by action type, plus a `Continue` action, the exported `sidesFor`, and the pure save format in `save.ts` (`toSave`, `fromSave`, `encodeSave`, `decodeSave`; ADR-0016).
- `src/adapters/` (S-010, ADR-0016) holds the driven adapters, the effectful edge that talks to the browser: today only `save-store.ts` (`createSaveStore`, which probes `localStorage` during construction, and `createAutosave`). Only `main.ts` imports it; domain, app and ui never do.
- `src/ui/` holds the effectful DOM renderers, built with `el()` (ADR-0002).
- `src/main.ts` is the composition root. It reads `location.search` once, owns the current state, and runs the loop `dispatch` then `update` then `render`.
- Dependencies point inward only: ui, then app, then domain; adapters sit beside ui (adapters may import app and domain, never ui; nothing but `main.ts` imports adapters).

Rejected simpler alternative: no layering, with generation inline in the UI. It breaks Node-only property tests and determinism checks.

### Earned Trust (probes)
S-001 has no external adapters. The only environment dependency is `location.search`, read once and validated by `parseSeed`, which falls back to the default on any bad input (the probe equivalent: the unit test feeds `abc`, empty, `9999999999`, `1.5`). ~~Storage will need a probe when persistence arrives (its own story).~~ (S-010, ADR-0016: persistence is the first driven adapter; `createSaveStore` probes `localStorage` during construction with a write-read-remove sentinel and degrades silently, and the decoder is strict. The nine lies and their fault scenarios are in ADR-0016 Earned Trust.)

### Enforcement
`.oxlintrc.json` forbids domain importing app or ui, app importing ui, and DOM/time use in domain. The PR guard rejects `Math.random`, `Date.now` and `new Date(` in `src/domain/`. Stryker mutates `src/domain/**` nightly.

### Domain model (S-001)
- `League`: `{ seed, clubs: readonly [8 Club] }`
- `Club`: `{ id, name, colours: readonly [Colour, Colour] }`; the colours are distinct and come from a fixed palette.
- Name uniqueness: 8 towns drawn without replacement from at least 24, plus a suffix that may repeat (ADR-0004).
- No external integrations, so no contract tests are needed.

### Squad (S-002, ADR-0005)
- Domain: `Player { name, position: GK|DF|MF|FW, age, overall }` (S-003 adds `attributes` and `condition`); `generateSquad(seed, clubIndex) => readonly Player[]` in `src/domain/squad.ts`; `deriveSeed(seed, stream) => number` in `rng.ts`.
- Different players per club by construction: one league-wide draw of 144 names without replacement from `FIRST_NAMES x SURNAMES`, sliced per club (stream `deriveSeed(seed, -1)`). Name-list entries are single words; pools are frozen after S-002 (changes reshuffle all squads). `clubIndex` not an integer 0..7 throws `RangeError`. Quota 2/6/6/4, ages 17-35, overall 1-20 (stored in S-002; derived from attributes since S-003, see below).
- Squad is derived on render from `league.seed` and the club's index; it is not in `GameState`.
- App: `Screen` adds `{ kind: "squad", clubId }`; `Action` adds `ViewSquad` (clubHome to squad) and `Back` (squad to clubHome); both are no-ops from other screens.
- UI: `ui/screens/squad.ts` `renderSquad(root, club, squad, dispatch)`; `club-home.ts` gains a "Squad" button and takes `dispatch`.
- Contract shapes: `generateSquad`, `deriveSeed` pure return-only (deep-equal, property tests); `renderSquad` bounded-change (root's children only); read-only driving ports expose no setters. No new external adapters, so no new probe; the only environment input stays `location.search` (S-001).
- No external integrations, no contract tests. No new C4 container: the existing L2 holds (domain gains `squad.ts`; the "Requests the generated league from" arrow also carries squads).

### Player detail (S-003, ADR-0006)
- Domain: `Player { name, position, age, overall, attributes, condition }`. `attributes` is a readonly record of `goalkeeping | defending | passing | shooting`, integers 1-20; `ATTRIBUTE_ORDER` and `ATTRIBUTE_LABELS` (exported from `squad.ts`) fix the display order and labels. `condition` is an integer percentage, generated 75-100 (`CONDITION_MIN`, `CONDITION_MAX`), constant in this story.
- `overall` is derived, not drawn: `deriveOverall(position, attributes)` = round-half-up of a per-position weighted mean, in integer tenths (GK 7/1/2/0, DF 0/6/3/1, MF 0/2/5/3, FW 0/1/3/6 over goalkeeping/defending/passing/shooting). Weights are non-negative and sum to 10, so `min attribute <= overall <= max attribute`, always within 1-20.
- Generation: the club stream `deriveSeed(seed, clubIndex)` still draws age then a 1-20 internal `quality` (so names, positions, ages and order are unchanged from S-002); attributes (quality plus a position offset plus noise -2..+2, clamped 1-20) and condition come from `deriveSeed(seed, 100 + clubIndex)`, five draws per player. Stream numbers in use: -1 names, 0..7 clubs, 100..107 attributes. Overall values differ from S-002 (no persistence; accepted).
- App: `Screen` adds `{ kind: "player", clubId, playerIndex }`; `Action` adds `{ type: "ViewPlayer", playerIndex }`, valid only from `squad` with a known club and an integer index 0..17, else a no-op. `Back`: player to squad (same club), squad to clubHome; no-op elsewhere. The player is derived on render (`generateSquad(league.seed, clubIndex)[playerIndex]`), not stored.
- UI: squad rows are `<li>` holding one `<button>` (the same four spans, 44px or taller); `renderPlayer(root, player, dispatch)` in `ui/screens/player.ts`. Label and value read on one line with a single space ("Position GK", "Goalkeeping 14", "Condition 92%"): inline flow only, no flex or grid on the pairs. Any attribute bar is a CSS pseudo-element (no DOM node, no text).
- Contract shapes: `generateSquad`, `deriveOverall`, `update` pure return-only; `renderPlayer`/`renderSquad` bounded-change (root's children only). No new adapters, so no new probe; no new C4 container.

### Tactics (S-004, ADR-0007, ADR-0008)

### Match (S-006, ADR-0010, ADR-0011)
- **Schedule** (new pure `src/domain/schedule.ts`, ADR-0010):
  - A seed-independent circle method over club indices 0..7, with 7 rounds and the second half mirrored (14 matchdays of 4 fixtures, each ordered pair exactly once).
  - Round `r`: {`r`, 7} with `r` at home when `r` is even; then {`(r+k) mod 7`, `(r-k) mod 7`} for `k` = 1..3, where the first is at home when `k` is odd.
  - Matchday 1 is `[0 v 7, 1 v 6, 5 v 2, 3 v 4]`.
  - `fixturesOf(matchday)` and `fixtureOf(matchday, clubIndex) => { index, fixture }` read a deeply frozen table. A bad matchday or club throws `RangeError`.
  - The seeded `league.clubs` order already varies who meets whom by name.
- **Model** (new pure `src/domain/match.ts`, ADR-0011):
  - `playMatch({ seed, matchday, fixtureIndex, home, away })`, where a side is `{ squad, xi }`. It returns `{ homeGoals, awayGoals, goals: { minute, side, playerIndex }[] }`.
  - Strength `S` = the sum of the XI's 11 overalls; the overall is already the position-weighted attribute rating (ADR-0006).
  - Conversion `p = 0.30 x S_own^3 / (S_own^3 + S_opp^3)`.
  - 9 chances per side, one per 10-minute window. Each chance always draws 3 floats (minute, conversion, scorer), so there are 54 draws per match whatever the XIs.
  - Scorer: weighted among the outfield starters by shooting x {DF 1, MF 2, FW 4}. Never the GK, no own goals, and no home advantage (out of scope).
  - Only exact or correctly rounded arithmetic (no `Math.pow`, `**`, `exp` or `log`), so every browser engine and Node agree.
  - Calibrated against the real generator (ADR-0011) on the canonical set: seeds 1..1000, the 4 matchday-1 fixtures each, 4000 matches, both sides automatic 4-4-2.
    - 1.363 goals per side, 0–0 in 5.5% of matches (220 of 4000), and at most 6 goals by one side.
    - The XI of each position's lowest-rated players scores 0.481 goals, against 1.384 for the automatic XI. A stronger XI never scores fewer on the same seed (monotone coupling).
    - Scorers: DF 12.5%, MF 36.3%, FW 51.2%.
    - A committed fixed-seed domain test reproduces this set.
  - Expected goldens (RED-first; DELIVER must match them, and changing them needs an ADR-0011 amendment): seed 31 reads "Netherwold Borough 1–2 Marlbrook Athletic"; seed 20260 reads "Harrowgate Lane United 0–1 Oakhampton Rise Borough". Goal lists are in port 20.
- **Stream**: `deriveSeed(seed, 200 + (matchday - 1) x 4 + fixtureIndex)`, that is streams 200..255. Table in use: -1 names; 0..7 clubs; 100..107 attributes; 200..255 matches.
- **App**:
  - `Screen` adds `match{clubId}`. `Action` adds `PlayMatch`, valid only from a known club's `clubHome`.
  - `Back` goes from match to clubHome. An unknown club is a no-op.
  - ~~`GameState` gains nothing: the result is never stored (D8).~~ Superseded by ADR-0012 (S-007): the matchday results are now recorded in `GameState.results` (see "Table and recorded results" below).
  - The pure selector `matchFor(state, clubId)` derives the match from `fixtureOf(OPENING_MATCHDAY = 1, clubIndex)` (S-008, ADR-0014: this derivation is now only the fallback when nothing is recorded; the selector reads the latest recorded matchday). The managed side uses `currentXI`; the other side uses `automaticXI(squad, DEFAULT_FORMATION)`. Since S-007 `playOpeningMatchday` produces the recording; `matchFor` reads it and, when none is recorded, falls back to the same producer (unreachable through `update`).
  - `focusPlan`'s `sameScreen` adds `match` (by `clubId`). Every navigation is a screen change, so focus goes to the `<h1>`.
- **UI**:
  - The club home gains a fourth `button.primary` "Play match".
  - `renderMatch` changes exactly this: `root.replaceChildren(<section class="match">)`, and the section has exactly these five children in order:
    1. `<h1 tabindex="-1">~~Matchday 1~~ Matchday N</h1>` (S-008, ADR-0014: the renderer prints the view's matchday, N = 1..14).
    2. `<p class="score-line">`: inline spans with literal single-space text nodes. `textContent` and `innerText` read exactly `Home 2–1 Away` (U+2013). It is styled as a scoreboard panel: chalk border, gold score, no flex or grid.
    3. `<p id="goals-label">Goals</p>`, with no `text-transform`.
    4. `<ul role="list" aria-labelledby="goals-label">`: items read exactly `23' Name (Club)` (inline spans). The list is rendered and visible (non-zero box) even when empty.
    5. A `.back-button` "Back".
  - Everything renders in one synchronous render, so the result is present when the `<h1>` is focused (D13).
- **Contract shapes and probes**: see the effect-isolation table and ADR-0011 Earned Trust: the Chromium-vs-Node golden in the e2e, inline-flow `innerText` checks, and the empty list probed through a seed pinned by a domain test. No external integrations, no contract tests, and no new C4 container (the domain gains `schedule.ts` and `match.ts`; the L2 holds, descriptions updated).

### Save and continue (S-010, ADR-0016)
- **What is saved** (one `localStorage` key, `gaffer.save`; envelope `{ v: 1, seed, clubId, formation, xi?, results? }`): the league's seed, the managed club, the formation, the XI only once the player changed it, and the results as per-match goal lists `[minute, side 0/1, playerIndex]` in schedule order (matchday, fixture, clubs and scores are derived from position and counts, so they cannot disagree). About 1.9 KB for an average season, about 10.5 KB at the theoretical maximum (guardrail 16 KB). Not saved: the screen, the league, squads, names.
- **Pure core** (`src/app/save.ts`): `toSave(state)` is `undefined` unless the screen carries a known club (so a new game in `pickClub` writes nothing, D4); `fromSave(raw: unknown)` is total and strict (version, int32 seed, club in the regenerated league, formation id, legal XI via `isLegalXI`, whole matchdays 1..14, well-formed goals, then a **replay-verify**: the 3 fixtures per matchday that do not involve the managed club must equal what the current model plays, via `sidesFor` and `playMatchday`). Anything off gives `undefined`; no partial restore. The restored state is the club home with the saved formation, XI and results (no new `GameState` key).
- **Continue**: `Action` adds `{ type: "Continue"; game: GameState }`, valid from `title` only (else a `toBe` no-op); `update` is turned into a handler table first (complexity 14 to 1), so the loop, `focusPlan` (heading focus on the club name) and the tests are unchanged. `render` is untouched (no new screen; its title case gains a prop, not a branch: still 15 of 15).
- **Adapter** (`src/adapters/save-store.ts`): `createSaveStore(() => localStorage)` probes while constructing (sentinel write, read back, remove) and degrades silently to "no store"; `read()`/`write()` never throw or log; `createAutosave(store, lastText)` writes after each dispatch only when `encodeSave(state)` is defined and differs from the last text. Triggers (club picked, formation, XI pick, Play match) and D4's timing fall out of `toSave`. The title reads the save once at boot; the `Continue` offer is a module constant of `main.ts`.
- **Title**: `renderTitle(root, { offer }, dispatch)`; with an offer, `button.primary` "Continue" above `button.secondary` "New game" (outlined gold, 48px); without, today's markup. h1 "Gaffer" focused on load; after Continue the club home h1 is focused (ADR-0008).
- **Determinism**: league regenerated from the saved seed, so "Play again" after "Continue" keeps that seed (D5); `nextMatchday` derived from the restored log; the continued season equals the uninterrupted one because `update` is a pure function of an equal state (K2).
- **Changed assumptions (S-010)**: S-007/S-008/S-009 "Results are kept until the page is reloaded" now reads "until the page is reloaded, then reachable through Continue"; ADR-0012 D9 "no persistence yet", ADR-0005 (d) "no persistence to migrate" and ADR-0006 "no persistence" now carry a cost: frozen squad, attribute and match tables are save-format-relevant (bump `SAVE_VERSION`, or replay drops the save); the S-009 "Play again keeps the league (same seed)" statement is unchanged and now applies to the saved seed.

    - `toSave` and `encodeSave` give `undefined` on `title`, `pickClub`, and for a club not in the league; on every other screen they project seed, club, formation, XI (only when stored) and the compressed log (only when recorded). The text is a pure function of the state: equal states give equal text; a navigation action, "Continue", a no-op pick or the same formation never changes it; a club pick, a changed formation, a changed XI and "Play match" always do. Full-season text is under 16 KB (average about 1.9 KB; a constructed 18-goals-in-every-match log about 10.5 KB).
    - **Round trip**: for a reachable state `s` on any club screen, `fromSave(JSON.parse(encodeSave(s)))` `toEqual`s `s` with the screen at `{ kind: "clubHome", clubId }`; `formation`, `xi`, `results` and `nextMatchday` are equal; the league deep-equals `s.league` (regenerated from the saved seed, so a saved seed 31 restores the seed-31 league even when the address holds another). Over seeds 1..300 x 8 clubs x matchdays 0..14 (untouched tactics) and over random formation, pick and Play match sequences with a restore at a random point (fast-check, `numRuns` 100, fresh `FC_SEED`): the rest of the season after restore gives the same results and table as the uninterrupted state.
    - **Strict decode, never throws, `undefined` otherwise**: arbitrary JSON values and strings, `null`, truncated text, a wrong or missing `v`, a non-int32 or non-integer seed, an unknown club, a bad formation, an XI that is not 11 distinct squad indices matching the formation's positions, `results` that is empty, not a multiple of 4 matches or over 14 matchdays, a goal with a minute outside 1..90 or decreasing, a side other than 0 or 1, a player index outside 0..17 or a goalkeeper scorer on the managed side, more than 9 goals for a side, and an unmanaged fixture that differs from the replay (the stored log of one matchday swapped, a goal's player changed). Every entry decodes whole or the save is dropped. 200 fast-check runs per CI run (K3).
37. **App: `update` with `Continue`** (pure; ADR-0016). `Action` adds `{ type: "Continue"; game: GameState }`. From `title` the result is `action.game` (the club home of the saved club); from every other screen the very same state (`toBe`). `GameState`, `Screen`, `focusPlan` are unchanged (title to club home is a screen change, so the plan is `heading`); no state holds a key beyond `league`, `screen`, `formation`, `xi`, `results`. `update` is now a handler table: every S-001..S-009 `update` case passes unedited. `NewGame` after `Continue` (from `seasonEnd`) keeps the restored league, so "Play again" keeps the saved seed.
38. **Adapter: the save store** (effectful, injectable; `src/adapters/save-store.ts`). `createSaveStore(getStorage, key?)` returns `{ health, read(), write(text) }` and probes during construction. Cases (fake storages in vitest): a getter that throws `SecurityError`; `setItem` that throws `QuotaExceededError` (sentinel, then only the save); `setItem` that silently drops the write; `getItem` that throws, or returns `null`, `undefined`, a number: in every case no exception, nothing logged (`console` spied), `health` "degraded" where the contract fails, `read()` `undefined`, `write()` a no-op; a healthy store round-trips text and leaves no `gaffer.probe` key. `createAutosave(store, lastText)(state)`: writes once per changed text, never for navigation, `Continue`, `NewGame`/"Play again" with no club, or a no-op pick; the first `ChooseClub` of a new game replaces the stored text (D4); a failing write is swallowed and not repeated until the text changes.
39. **UI** (roles and accessible names, 390px; the title):

| Screen | Contract |
|---|---|
| Title, no saved game (first visit, fresh browser, unreadable save, blocked or full storage) | Exactly as before S-010: one `<h1>` "Gaffer" focused on load, one `button` "New game" (the primary gold button); no button named "Continue" |
| Title, saved game | One `<h1>` "Gaffer" (the only heading, focused on load), a `button` named exactly "Continue" (44px or taller) immediately above the `button` named exactly "New game" (44px or taller, the outlined secondary style). No other new text or control. "Continue" lands on the club home of the saved club (`<h1>` = club name, focused): "Table" shows the same rows cell for cell, "Tactics" has the saved formation checked, "Starting XI" the same 11 texts in order, the next "Play match" is "Matchday N+1", a finished season shows "End of season" and no "Play match", "End of season" shows the same lines. "Continue" ignores the address's `?seed=` (D5). No sideways scroll at 390px, no console errors |

Cross-cutting: locators use `exact: true` for "Continue", "New game" and the h1 ("Continue" is not a substring of any generated name: unit check over `names.ts`); each Playwright test has a fresh context, so storage starts empty (protected S-001..S-009 scenarios see the unchanged title); within one test repeated `page.goto` and `page.reload` share storage, which is fine because "New game" always starts fresh; e2e that corrupt, block or fill storage do so with `page.addInitScript` or `page.evaluate` and live in non-protected specs.
